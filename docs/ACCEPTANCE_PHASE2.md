# Phase 2 acceptance report — real AI song-generation vertical slice

Date: 2026-10-26. Branch `ccr-936b65c0-6lt7lb`.

## Verdict

**Not accepted.** The acceptance condition is *a real authorized voice producing a real song
through a real AI provider, playing in DeenVoice, persisting, with measured cost and a
listening result*. **That did not happen and could not happen in this environment.** No
provider API was called, no voice was enrolled with a provider, no song was generated by an
AI, and nothing was heard by a listener. Nothing below should be read as evidence that any
provider can sing in a cloned voice, or can sing Hausa or Arabic.

What *was* built and verified is everything around the provider call: the product plumbing
that a real provider will plug into, tested end to end with a **labelled test double** (a
synthetic tone), plus the tools and the runbook to run the real proof on a machine that can
reach the provider.

### What the real-browser run covers

Sign up (client-side 10-character rule), operator grants credits, **page reload keeps the
session**, add a voice (the **server's consent text** shown; checkbox + file required),
"Processing…" → ready, Hausa refused because the engine does not declare it, choose English,
Generate, job followed through its real stages, **Play**, "Made with test-double" shown,
audio fetched and playing, **reload → song still in My Songs → plays again**, credits 3 → 2
(reserved then captured), sign out, a second account cannot see the first's songs.

### What that run does **not** show

That an AI can sing in anyone's voice; that Mureka's API looks like the adapter assumes; that
any audio is musical, similar, correctly pronounced or acceptable to a listener; any latency
or cost figure from a real provider. The tone it plays is generated by the test double.

## Unsupported or unproven requirements

- **Singing in a cloned voice** — no evidence beyond Mureka's documentation (via search), never exercised.
- **Hausa singing** — **no researched provider documents it; Mureka's documented vocal languages (English, Chinese, Japanese, Korean, Portuguese, Spanish, German, Italian, French, Russian) exclude it.** The app therefore does not offer Hausa to an engine that does not declare it.
- **Arabic singing** — not in Mureka's documented list; unverified elsewhere.
- **Voice deletion at the provider** — no self-service API found; "by request" only.
- **Commercial rights and data licence** — API agreement assigns output to the customer (per search summaries) but also grants Mureka a sub-licensable licence over uploaded personal data; needs counsel before real users.
- **Output retention** — the provider keeps results up to about one month; the backend downloads and stores its own copy.

## Costs

Spent in this phase: **$0** (no provider call). Rate card (to be reconciled with an invoice): $5 per
Vocal ID, ≈ $0.045–$0.15 per lyrics → song. Model, worked example and the unknowns (failure billing,
real completion rate) are in [poc/COST_MODEL.md](poc/COST_MODEL.md). The backend already reports cost
per **successful** song including billed-but-failed attempts.

## Security considerations

- Keys: provider key only in the server environment; the app holds the user's session token only.
- Session token is in browser storage on web — fine for a trial, not for release (BACKEND.md).
- Untrusted provider URLs are constrained (https, no IP/localhost, optional allow-list, size cap, no key sent).
- Provider text never reaches users; secrets, lyrics and audio never reach logs/audit (tested).
- Open registration is safe only while credits are operator-granted.
- A person's voice is biometric-adjacent data: consent, deletion and the provider's reuse rights are
  the main risks; misuse reporting and moderation do not exist yet.

## Remaining production gaps

See [BACKEND.md](BACKEND.md#production-gaps). In short: managed DB/KMS/object storage, session hardening,
payments, abuse tooling, webhooks, observability, legal review, Android/iOS verification, a lyrics model,
and — most importantly — **a real provider result that a native Hausa speaker has judged**.

## How to complete the acceptance (in order)

1. Unblock the hosts and provide the key (table above).
2. `node backend/scripts/mureka-probe.mjs --discover` → set `MUREKA_VOCAL_CLONE_PATH`; fix the adapter's field names if the page differs.
3. `--billing`, then one `--generate … --spend` without a voice (~$0.05) to confirm the song contract.
4. `backend/scripts/live-poc.ts` with the participant's sample and original English lyrics.
5. Hausa and Arabic probes with `EXPERIMENTAL_LANGUAGES`, recorded as experiments.
6. Listening evaluation with native raters; `summarize-listening.ts`.
7. Play it in the app (`API_BASE_URL`), reopen from the library, reconcile cost, delete the participant's data.

Accept only if every item in the criteria table is green **and** the listening result meets the
pre-registered bar for each language claimed. If Mureka cannot sing in the participant's voice, stop,
report that, and evaluate the next candidate; do not simulate.
